# Taiga MCP Server


Full-featured MCP (Model Context Protocol) server for [Taiga](https://taiga.io) project management. Provides comprehensive access to Taiga's API v1, enabling AI agents to manage projects, epics, user stories, tasks, issues, sprints, wiki pages, memberships, roles, and more.

## Features

Covers **all** Taiga API v1 endpoints:

- **Projects** — CRUD, stats, tags, likes, watching
- **Epics** — CRUD, bulk create, related user stories, voting, watching, attachments
- **User Stories** — CRUD, bulk operations, ordering, Sprint-to-Backlog (`taiga_userstory_move_to_backlog`: clears the Sprint assignment safely, verified, idempotent), voting, watching, attachments
- **Tasks** — CRUD, bulk create, voting, watching, attachments
- **Issues** — CRUD, bulk create, Sprint-to-Backlog (`taiga_issue_move_to_backlog`: clears the Sprint assignment safely, verified, idempotent), voting, watching, attachments
- **Milestones/Sprints** — CRUD, stats, watching
- **Wiki** — Pages & links CRUD, watching, attachments
- **Memberships** — CRUD, bulk invite
- **Roles** — CRUD with permissions
- **Users** — List, get, me, stats, contacts
- **Statuses** — US/Task/Issue statuses, types, priorities, severities, points
- **Custom Attributes** — Definitions & values for epics, user stories, tasks, issues
- **History & Comments** — Change history, create/delete comments
- **Search** — Global project search
- **Timeline** — User & project timeline
- **Resolver** — Slug/ref to ID resolution
- **Webhooks** — CRUD, test, logs
- **Export/Import** — Project export & import

### MCP Client Configuration (recommended)

The easiest way to use this server is via `npx` — no installation required:

```json
{
  "mcpServers": {
    "taiga": {
      "command": "npx",
      "args": ["-y", "taiga-mcp"],
      "env": {
        "TAIGA_URL": "https://taiga.example.com",
        "TAIGA_USERNAME": "your-user",
        "TAIGA_PASSWORD": "your-pass"
      }
    }
  }
}
```

> **VS Code / GitHub Copilot** — add the entry above to your `mcp.json`.  
> **Claude Desktop** — add it under `mcpServers` in `claude_desktop_config.json`.

## Executable workflow contract

In a project whose Task statuses are To Do, In Progress, GPT Validation, Human Decision, Done and Cancelled (plus the optional `Request`), every Task status change goes through `taiga_workflow_transition` with a typed `artifact` and an actor/state matrix; see `knowledge-base/RULES.md` (Guide 5, "Executable workflow contract") for the full rules.

- **Templates** live in `workflow/templates/<name>-vMAJOR.MINOR.PATCH.md` (one short description per field). New artifacts use the highest SemVer version; existing ones are read with the version they declare; anything malformed fails closed. Read one with `taiga_workflow_template` (`format` = `raw` (default) | `parsed` | `both`; the `.md` is the only source of truth and the parsed view is derived from it at runtime; without `version` the highest SemVer is used, so a new `1.0.1` file needs no code change). Enumerations such as `request_type` come from the template, not from code.
- **Actors**: `TAIGA_MCP_ACTOR=gpt|claude|po` in the environment of the process that launches this MCP (one process per agent), or `TAIGA_MCP_GPT_TOKEN` / `TAIGA_MCP_CLAUDE_TOKEN` / `TAIGA_MCP_PO_TOKEN` (16+ chars, distinct) for the HTTP transport. Without either, identity is syntactic and every workflow mutation in a strict project is rejected (`WORKFLOW_IDENTITY_REQUIRED`); reads keep working.
- **Common artifact header**: every governed artifact starts with the real status movement (or `Status unchanged`; a Human Decision Resolution shows the intended manual PO move `Human Decision → GPT Validation`, nothing moved), `Schema: <Name> <version>`, `Author` (the authenticated actor), `Model` and `Effort`. `Model` / `Effort` are declared by the agent on each call (`model`, `effort` parameters), `Unknown` when absent or invalid, and never affect authorization; they do not come from the launcher environment.
- **Statuses by name**: `taiga_workflow_transition` takes the status NAME (`"In Progress"`, `"GPT Validation"`, `"Request"`...) and resolves the project's real id at runtime; unknown or ambiguous names fail closed and no id is written in rules or logic (see RULES Guide 5).
- **Entity identity**: Task, User Story, Epic and Issue get a `UUID` custom attribute (UUIDv7) from the MCP. `taiga_uuid_initialize_project` (dry run by default) makes a project UUID-ready, `taiga_uuid_resolve` maps a UUID to its entity, and `taiga_uuid_backfill` is a deprecated alias of the initialize operation. Rules: RULES Guide 5, "Entity identity".
- **Tools**: `taiga_task_workflow_state`, `taiga_workflow_request_create`, `taiga_workflow_request_answer`, `taiga_human_decision_resolve`, `taiga_workflow_template`, `taiga_uuid_initialize_project`, `taiga_uuid_resolve`.
- **Human Decision resolution** (`taiga_human_decision_resolve`, template `human-decision-resolution`) is NOT a transition. Flow: `Human Decision` -> the PO decides outside Taiga -> GPT records a `human_decision_resolution` (the PO is the decision authority, the author only records it) -> the MCP persists and reads back the artifact, then clears `is_blocked`/`blocked_note` if set (nothing to do when already unblocked) -> the Task STAYS in Human Decision -> the result and `taiga_task_workflow_state.human_decision` give `next_status`/`next_owner` and `ready_for_po_move` -> the PO reads the handoff and moves the Task manually. The artifact's first line reads `Human Decision → GPT Validation` (never `Status unchanged`): it is the INTENDED movement the PO performs manually, not a transition the MCP executed (a `Movement: intended, not executed` line says so). Only GPT or the PO can call it; Claude cannot; nobody but the PO moves the Task out of Human Decision. It resolves the latest unresolved Human Decision Request (`decision_request_comment_id`; stale, unknown or already-resolved ids are refused), `next_status` is always `GPT Validation` and `next_owner` always `gpt` (template 1.1.0 enums), whatever status the Task entered from. Human Decision is a PO-owned stop. A resolved Human Decision never releases execution directly. After the resolution is persisted, the PO manually moves the Task to GPT Validation. GPT reconciles the decision with the Task contract and either validates the existing implementation or issues the appropriate Blueprint before execution resumes. If the Task has no Blueprint yet (To Do -> Human Decision -> GPT Validation), GPT Validation -> In Progress carries the initial Implementation Blueprint (round 1) instead of a Correction Blueprint; with an existing Blueprint it still needs a Correction Blueprint. Resolutions recorded before this rule (template 1.0.0) stay readable history and are not edited. If the artifact persists but the unblock fails the call returns `WORKFLOW_INTEGRITY_FAILURE` (never success) and repeating the same call completes the unblock without a second artifact. A later entry into Human Decision starts a new independent round. Read model: `decision_status` pending|resolved, `ready_for_po_move` (resolved AND unblocked), `next_status`, `next_owner`; `owner_role` stays `po` while the real status is Human Decision.
- **Request** is a workflow-closed status (strictly limited transitions) but NOT `is_closed=true` (it stays open): entry only by Claude from In Progress; exits only resume (Claude), Human Decision (GPT/PO) and Cancelled (PO). **The current Taiga status is the only authority.** Card = Request means Request, card = In Progress means Claude may implement, whatever the comments say. The Workflow Request / Response / Resume comments are append-only EVIDENCE: they never authorize, block or veto a transition, a manual PO move of the card is honored on the next read, and a Task can cycle Request -> In Progress -> Request any number of times with no one-time-use bookkeeping. `request_resume` is authorized by the status and the actor matrix alone; its `request_id` and `response_comment_id` are citations, and one that does not line up with the history (no answer, a partial answer, another request, a reused request, a changed Blueprint) is returned as `evidence_warnings` on the result, never as a rejection. `taiga_task_workflow_state` reports `request_status` from the status only (`in_request`, `claude_may_implement`, `awaiting_response_from`), lists the parsed requests under `request_evidence` (with a note that it is not state) and no longer exposes `has_blocking_request`; continuation recovery emits a Request obligation only for a Task visibly in Request. The `R-<ref>-<n>` id of a new request is just the next free label in the history, not a counter that decides anything.
- **Bridge notifications (optional)**: `TAIGA_MCP_NOTIFY_COMMAND='["node","/scope/claude-bridge/probe/ctl.ts","notify"]'` makes the MCP emit a typed pointer after Taiga persisted the event; unset = disabled.
- **Rejections** are structured (`code`, `required_artifact`, `required_version`, `missing_fields`, `invalid_fields`, `template_path`, `allowed_actions`, `next_step`) and mutate nothing.
- **REST bypass closure (prepared)**: `scripts/taiga-rest.ts` + `ops/rest-closure/` (see its README).
- **Signing key generator**: `npm run auth:keygen` prints exactly three lines (`Private Key:` PKCS#8 DER Base64, `Public Key:` SPKI DER Base64, `Key ID:` lowercase hex SHA-256 of the public DER bytes), writes no file and names no variable. The operator copies the private key by hand into the real `.env` as `TAIGA_MCP_MERGE_AUTH_PRIVATE_KEY_B64` (empty placeholder in `.env.example`; `.env` is git-ignored) and the public key into GitGate's `.env` as `GITGATE_MERGE_AUTH_PUBLIC_KEY_B64`. Never paste a key into Git, Taiga, Bridge or logs. The bootstrap pair is temporary (agents can reach it today). Isolation cut-over: run the same command on the isolated Taiga MCP host, replace the private key there and the public key in GitGate, confirm the new Key ID, retire the bootstrap pair; configuration only, no code change.
- **Signed merge authorization** (`src/workflow/merge-auth.ts`): the approval that moves a Task or Story to Done may carry `merge_context` `{repository, source_branch, target_branch, source_sha, target_sha}` (SHAs are 40-digit lowercase hex; the source branch must be `feature/task-<ref>-...` or `feature/story-<ref>-...` of the approved item; the target branch is checked against Taiga: a Task merges only into `feature/story-<ref of its parent Story>-...`, a Story only into `feature/sprint-<id of its Sprint>-...`, never `main`). The context, the parent Story/Sprint (same project), both UUIDs and the key `TAIGA_MCP_MERGE_AUTH_PRIVATE_KEY_B64` (PKCS#8 DER Base64 Ed25519, from `npm run auth:keygen`) are checked BEFORE any mutation; a missing or invalid key or context refuses the call. Only after the Done is persisted and re-read the result carries `merge_authorization` = `{version: 1, claims, signature}`: claims `issuer`, `key_id` (sha256 of the public SPKI DER), `action` (`task-done` or `story-done`, derived from the entity, never from the caller), `authorization_id`, `project`, `work_item` (`Task <uuid> (#ref)` read from Taiga), `target_work_item` (the parent `Story <uuid> (#ref)`, or `Sprint #<id>` since Sprints have no UUID), plus the five context fields; `repository` is a supplied git coordinate that the verifier (GitGate) must check itself; the signature is Ed25519 over the claims as JSON with sorted keys. If signing fails after the Done, the Done stands and the result has `merge_authorization_error` (do not retry). `verifyMergeAuthorization(envelope, publicKeySpkiDerB64)` is the pure offline check. Delivery to the other agent is a separate Task; this does not block raw Git. Rotation changes only the environment value and the verifier's public key. Local config: the private key lives only in the git-ignored root `.env` (next to `.env.example`); the MCP does not read `.env` itself, so a running instance gets it from its launcher environment (loading it live is a restart step). To replace the key, run `npm run auth:keygen`, put the new Private Key in `.env`, give the verifier the new Public Key, and restart.
- **Signed authorization on the completion notice**: with `TAIGA_MCP_NOTIFY_AUTH_STDIN=1` (default off) the exact `merge_authorization` envelope is written to the notify command's STDIN as `{"authorization": <envelope>}`, only for `TASK_DONE` and `STORY_DONE` notices that follow a Done with `merge_context`, and for `SPRINT_CLOSED` from `taiga_milestones_close`, never on argv and never for any other event (stdin is otherwise closed empty). The envelope is always also in the transition result, with `merge_authorization_handoff` = `attempted_unconfirmed` when the payload was written and the notify command exited 0 (an exit code proves neither that the notifier read stdin nor that anything was stored, so delivery is never reported as confirmed), `failed` when the payload was written but the notification failed, `not_attempted` when it did not travel (opt-in off or not a completion notice); a failed notification never undoes the Done and the approval is never repeated. The Bridge MCP `ctl.ts notify` stores it as the optional `notice.authorization` field; enable the flag only for a notifier that reads stdin.
- **Sprint close** (three governed phases; the Sprint stays OPEN until the GitGate merge AND the removal of the Sprint source branch are proven): (1) `taiga_milestones_prepare_close` (GPT or PO) takes `merge_context` (branch `feature/sprint-<id>-...`; the Sprint to the integration branch), checks the signer, the context, that the Sprint is open and not already prepared, that EVERY Story of the Sprint is semantic Done (one predicate, `sprintScopeProblem` in `src/workflow/story-readiness.ts`: status resolved by NAME, never by id or `is_closed`; Cancelled is NOT accepted scope; an empty Sprint passes; a refusal names each non-Done Story and writes nothing), signs `action: sprint-done` (`work_item` `Sprint #<id>`, `target_work_item` `Project #<id>`) with the Taiga key, stores the envelope as the durable merge-ready record (Taiga wiki page `merge-ready-sprint-<id>` of the Sprint's project, written and re-read) and emits `SPRINT_CLOSED` (GPT only; the PO is not a Bridge party) with status `Merge ready; Sprint still open` and the same stdin handoff and `merge_authorization_handoff` semantics as above; no `closed=true` is written and a second authorization is never issued. (2) `taiga_milestones_confirm_merge` (GPT, Claude or PO) takes `{id, receipt}`: the GitGate completion receipt described next. Nothing the caller asserts outside the signed receipt is trusted. A receipt that is authentic and bound but whose branch is not yet removed is stored and leaves the Sprint not terminal-ready (`terminal_ready: false`); a newer receipt for the same merge may add the cleanup, signed evidence can never be withdrawn, a different `final_integration_sha` is refused, an exact repeat is idempotent and writes nothing. (3) `taiga_milestones_close` (GPT or PO, only `id`) is refused unless every Story of the Sprint is still Done (the same `sprintScopeProblem`, re-checked at the terminal step) and the stored receipt verifies and signs both removals true, then persists `closed=true` and re-reads it; it emits nothing and signs nothing. It is idempotent (Issue #343): a Sprint that is already closed succeeds (`idempotent: true`, no second write) only when the stored authorization and GitGate receipt still verify, otherwise it is refused as closed-but-unproven; if the PATCH was acknowledged but the re-read cannot show `closed=true`, the result is the error `PERSISTED_OR_UNKNOWN` with `reconcilable: true` (not a definitive failure): call close again to converge. `taiga_milestones_update` with `closed: true` is refused before any write. The merge-confirmation predicate (`mergeConfirmationProblem` in `src/workflow/merge-ready.ts`) gates only `taiga_milestones_close`; the final Sprint Task is NOT gated on it, because prepare requires the `FINAL Sprint Engineering Review` Story to be Done and that Story needs its final Task Done first (canonical order: final Task Done -> FINAL Story Done -> prepare -> confirm -> close, acyclic). It re-verifies the stored authorization with the Taiga key and the stored receipt with the GitGate key on every call, so the wiki page is never a security boundary and a missing key fails closed. A Sprint has no parent or completion Issue (PO decision). Sprints closed before this flow stay readable and are not migrated.
- **GitGate completion receipt (trust root separate from Taiga, PO Human Decision Option A)**: GitGate owns its OWN Ed25519 key pair; the Taiga MCP key signs only Taiga-owned authorizations and never GitGate evidence, and the GitGate private key never lives here. Configure the PUBLIC key with `TAIGA_MCP_GITGATE_PUBLIC_KEY_B64` (SPKI DER Base64 Ed25519; missing or invalid fails closed). The receipt is the JSON object `{version: 1, issuer: "gitgate", key_id, authorization_id, repository, source_branch, source_sha, target_branch, target_before_sha, final_integration_sha, outcome: "merged", local_branch_removed, remote_branch_removed, signature}`; `key_id` is the sha256 hex of the SPKI DER public key; `signature` is Ed25519 (Base64) over the UTF-8 JSON of every field EXCEPT `signature` with keys sorted lexicographically (`canonicalReceipt` in `src/workflow/merge-auth.ts`); `authorization_id` and the context fields must equal the stored authorization claims (`target_before_sha` is its `target_sha`); unknown fields, a wrong key id, a bad signature or any mismatch are refused before any write. This is the contract GitGate's Sprint completion output (GitGate Task 123) must emit. A future LangGraph orchestrator (ADR-0090) may carry the receipt to `taiga_milestones_confirm_merge`, but it is neither a signer nor a second state owner.

## Durable workflow continuations (consumer contract, Issue #335)

A Bridge notice is best-effort transport: its `sent` only means the notifier process ran. The durable truth that "a persisted workflow boundary created work for an actor" is a **continuation**, owned by this MCP (never by the Bridge, never by a runner). A future LangGraph runner can consume the same contract unchanged; nothing here depends on it.

- **Persistence**: every Bridge-typed notice (task released/returned/in GPT Validation/Done, Request opened/answered/resolved, Story Done, Sprint merge-ready) and the mechanical Story readiness promotion (`STORY_READY_FOR_VALIDATION`, to `gpt`) write one continuation BEFORE any dispatch, so an offline or failing Bridge cannot erase it. Store: append-only JSONL `continuations.jsonl` next to `governance.json` (`TAIGA_MCP_CONTINUATION_FILE` overrides; git-ignored runtime state shared by every MCP process on the machine, so it survives restarts). A torn tail line is skipped.
- **Identity** (deterministic, idempotent): `<type>:p<project>:<task|userstory|milestone><ref>:<source>` where `source` is the persisted artifact comment id (or the authorization id for a Sprint). A duplicate emission or replay folds to ONE logical continuation. Fields: `id, type, to (gpt|claude), from, entity, ref, project, source, request_id?, status?, created_at, state, delivered_at?, handled_at?`. `to` is the semantic actor, never a session detail; for a Bridge notice it is the other party.
- **States**: `pending` -> `delivered` -> `handled`. `delivered` only records that the consumer saw it and never closes it; only `handled` closes it. Both acks are idempotent and never go backwards.
- **Read**: `taiga_continuations_pending` (`project?`, PO-only `actor?`) lists the caller's open continuations (pending or delivered). GPT and Claude see only their own.
- **Ack**: `taiga_continuation_ack` (`id`, `ack: delivered|handled`). Only the addressee (or the PO) may ack; an unknown id is refused; identity must be authenticated. Mark `handled` only after re-reading Taiga (`taiga_task_workflow_state`) and completing or deliberately resolving the authorized next step.
- **Recovery from Taiga (the ledger is derived state)**: `taiga_continuations_pending` first rebuilds any missing continuation from the AUTHORITATIVE Taiga state of the project's open Sprints (`continuation-recovery.ts`): Task In Progress with its current Blueprint (released / returned), GPT Validation with its latest Execution Handoff, Done with its Validation Approval (only while the parent Story is not finished), open Workflow Requests, a resolved Request on a Task in `Request`, a Story in GPT Validation whose latest predecessor is a readiness promotion, and an approved Story. It uses the same `continuationOf` identity and the same source comment id as normal emission, so a recovered and an originally recorded obligation are ONE; an id already in the ledger (pending, delivered or handled) is never touched, so a rebuild cannot resurrect a handled item. It reads Taiga only (never Bridge state), auto-handles nothing and never retries a transition. The result reports `recovery: {recovered}` or `{error}`; a Taiga read failure does not hide what the ledger holds. Scope limit: closed Sprints are not re-opened, so after a total ledger loss only the current open-Sprint state is rebuilt.
- **Handled survives ledger loss**: `taiga_continuation_ack` with `ack=handled` first writes ONE internal, non-authoritative "Continuation Handled" comment (template `continuation-handled`, `Status unchanged`, Author = the acknowledging actor, `Continuation: <exact id>`) on the task or Story the continuation is about, and only then the ledger line; if the Taiga write fails nothing is acknowledged and the ack is simply retried. Recovery reads those markers from the card history it already fetches and never rebuilds a continuation proven handled, so after a total ledger loss handled Done work stays gone while genuinely outstanding Done work is rebuilt with the same id. A repeated handled ack writes no second marker. `delivered` stays ledger-local (a delivered-only item is rebuilt as pending). Derived state: the ledger and its delivered marks; durable evidence: the handled marker. Sprint continuations have no card history, so they keep ledger-only handled state. Deploying this template needs a restart of every MCP process (an older process fails closed on the unknown template).
- **Not authority**: a continuation never executes or authorizes anything, the MCP never auto-resumes a transition because one exists, and the Bridge stays transport-only (`act:false`). Recording failures are reported next to the result (`continuation: {id, recorded}`) and never undo the persisted workflow mutation.

## User Story lifecycle (strict Story vocabulary)

Task: `To Do -> In Progress -> GPT Validation -> Done`.
Story: `Ready -> In Progress -> GPT Validation -> Done` (Human Decision / Cancelled stay supported escape states on the commented path).

| Story transition | Actor | Artifact |
|---|---|---|
| Ready -> In Progress | GPT / PO | `story_start` |
| In Progress -> GPT Validation | GPT / PO (never Claude) | `story_validation_handoff` (cumulative; every child Task must be Done or Cancelled) or, automatically, `story_readiness_promotion` |
| GPT Validation -> In Progress | GPT / PO | `story_correction` (cites the latest Story handoff) |
| GPT Validation -> Done | GPT / PO | `story_validation_approval` (cites the latest Story handoff) |

- Claude executes the child Tasks through the unchanged Task workflow; Claude never starts, promotes, corrects or closes a Story.
- When a child Task reaches Done or Cancelled and EVERY child Task is then terminal, the MCP itself promotes a Story that is In Progress to GPT Validation (PO decision, Issue #335) and writes one mechanical `story_readiness_promotion` comment (triggering Task and child statuses only; no acceptance, test or commit evidence). It never closes the Story: Story Done stays an explicit GPT/PO `story_validation_approval`, which cites that comment (or a manual `story_validation_handoff`) as its readiness predecessor. The readiness comment is proven first and the status write follows, so a Story is never in GPT Validation without its predecessor and nothing needs compensation (a failed or lost status write leaves the Story In Progress and the unused comment is reused by the next attempt; a replay finds the Story no longer In Progress); a failure is reported as `story_promotion` next to the Task result and the Task transition stays valid. Separately, this Taiga may physically mark the Story `is_closed=true` and fill `finish_date` when every child Task closes, BEFORE the SCOPE approval of the Story; that is known upstream behaviour and does not mean the Story is Done. The explicit In Progress -> GPT Validation transition remains for a Story that was not auto-promoted; it re-reads every child Task at call time and refuses (before writing anything) unless each one is semantically `Done` or `Cancelled` by status name: `is_closed` alone or a Story with no child Task do not qualify. The rejection names the blocking Task refs and statuses.
- Story promotion is aggregate and explicit; Story-level validation is cumulative (the approval audits the whole Story, not the last patch).
- The Story STATUS is the only lifecycle authority: Done and Cancelled => workflow ended; Ready, In Progress, GPT Validation, Human Decision => workflow open. `userstory.is_closed` and `finish_date` are upstream metadata derived by Taiga from the child Tasks (writes to them are ignored, proven by a live probe, Issue #243); the MCP never writes or validates them for a Story, and they never decide state, owner, transition, validation or completion. The Story transition PATCHes the status and rereads it, failing with `WORKFLOW_INTEGRITY_FAILURE` if the status differs from the target. The `closed` field of a Story transition result is the SCOPE meaning of the status, not the physical `is_closed`. For Tasks nothing changed: closure is derived from the status, proven by reread, and a Task status definition whose own `is_closed` contradicts it fails closed before any write.
- Direct lifecycle mutation is forbidden under governance: `taiga_userstories_update` / `taiga_tasks_update` and the create tools refuse `is_closed` (and `status`) in a project that exposes the strict vocabulary. Governance OFF and non-strict projects keep the legacy behaviour; Epics are unchanged.
- Task precedence has one governed operation: `taiga_move` with `kind: "task"` (moves the Task inside its own taskboard column by `taskboard_order`, the only Task position in this MCP, and fails closed if the visible order does not verify; `us_order` is never exposed). In a strict project `taiga_tasks_update` refuses `taskboard_order` and the `taiga_tasks_bulk_update_taskboard_order` tool is refused. Governance OFF and non-strict projects keep the low-level paths.
- **Account binding** (`src/workflow/account-binding.ts`): the actor (TAIGA_MCP_ACTOR / bearer role) says who is calling; the Taiga login says which account the process is. `TAIGA_MCP_EXPECTED_ACCOUNT_GPT|CLAUDE|PO` hold the Taiga username each role must be logged in as (values come from the deployment, never from source). With none set the binding is off (legacy behaviour); once ANY is set it is on, and every governed workflow mutation (transition, Workflow Request create/answer, Human Decision resolve) first reads `GET /users/me` (once per Taiga login, re-read after a new login) and is rejected with `WORKFLOW_IDENTITY_MISMATCH`, before any write, when the actor has no expected account configured or the process authenticated as a different account. There is no fallback to another account and no inference from model names or display names. Each launcher therefore sets its own `TAIGA_USERNAME`/`TAIGA_PASSWORD` (ChatGPT account for the GPT launcher, ClaudeCode account for the Claude launcher, the PO account only on an explicit PO runtime) plus the matching expected-account variable. Reads stay available.
- **Assigned projection** (`src/workflow/assignment.ts`): Taiga's Assigned field is a visual projection of the authoritative workflow owner and is never read to authorize, order or rebuild state. On every governed status write (`taiga_workflow_transition`, and the mechanical Story promotion to GPT Validation) the owner of the target status is resolved BEFORE any write and sent in the same PATCH as the status, then reread and verified. Mapping: Task and Epic follow the status owner (To Do/GPT Validation/Request -> GPT, In Progress -> Claude Code, Human Decision -> PO; Request is always addressed to GPT); a User Story is orchestrated by GPT/PO (Ready/In Progress/GPT Validation -> GPT, Human Decision -> PO); Done/Cancelled are not projected. The Taiga user is the active project member whose username is the configured `TAIGA_MCP_EXPECTED_ACCOUNT_<ROLE>` (no ids are stored). With none configured the projection is off; once any is set, a role without an account, or an owner that is not exactly one active member, rejects with `WORKFLOW_ASSIGNEE_UNRESOLVED` and writes nothing. Stand-alone Workflow Requests do not move the card and do not change Assigned.
- **Initial Assigned and backfill** (`createdWithOwner`, `backfillSprintAssignees` in `src/workflow/assignment.ts`): a card CREATED in an owned status never passes through a transition, so every Task and User Story creation path (`taiga_tasks_create`/`bulk_create`, `taiga_userstories_create`/`bulk_create`, the Epic related-stories bulk create, `taiga_issues_promote_to_userstory`) first resolves the owner of the initial status (the given one, else the project default: Task To Do and Story Ready -> GPT) with the same resolver, creates nothing when it cannot be resolved (`WORKFLOW_ASSIGNEE_UNRESOLVED`), then assigns every created row and rereads it (a mismatch is returned as `assignee_integrity` on the row, never hidden). `taiga_assignees_backfill {milestone, dry_run}` (default dry run) repairs the open Tasks and Stories of one Sprint: the target comes only from each card's current status through the canonical resolver, only `assigned_to` is written (status, order, history and watchers are untouched), Done/Cancelled and ownerless statuses are skipped, and a second run changes nothing. Watchers are independent subscription metadata: they never decide or satisfy Assigned.
- **Governed write boundary** (`src/workflow/mutation.ts`, `src/workflow/validators.ts`): every governed workflow write follows ONE pipeline, `mutate`: fresh Taiga `read` -> separate validators (all before any write; a refusal writes nothing and is returned as `WORKFLOW_PRECONDITION_FAILED`) -> the action's declarative write -> the boundary itself runs `read` AGAIN and hands that authoritative `after` state to the REQUIRED `verify` step (a mismatch is REPORTED as `integrity`, never retried or rolled back; status stays authoritative). `read` must be a real Taiga read, never a create/PATCH response or a caller snapshot, and `mutate` throws before any read or write when `verify` is missing. Nothing survives the call: no cache, snapshot, webhook or memory; Taiga is the only state. The write callback receives a `Writer` (`comment`, `patch` with a fresh version unless the caller passes one on purpose, `create`, `wikiCreate`, `wikiUpdate`) and nothing else, and the boundary holds no business rule. Migrated governed paths: the status transition (artifact comment + status/assignee/blocking PATCH), the mechanical Story promotion, the Workflow Request / response / Human Decision comments and the unblock, the continuation-handled evidence, the Assigned projection (creation and backfill), the merge-ready wiki record and the FINAL review Story/Task creation and Sprint reorder. `test/write-boundary.test.ts` fails the build when any other module in `src/workflow` calls `client.post/patch/put/delete`, the comment writers or `writerFor` (business modules use `mutate`), or has a `mutate()` call without its `verify`. Not governed on purpose: the administrative tools in `src/tools` (profile, custom attributes, generic CRUD). Validator registration pattern: write a small `(fresh state) => string | null` function (see `storyHasChildTask`) and list it in `validators` of the `mutate` call that needs it. Story-has-Task: a User Story cannot go Ready -> In Progress without at least one child Task.
- **Start order and one active Task** (`src/workflow/start-rules.ts`), in plain language: the order you SEE in Taiga is the order of execution. When GPT or Claude moves a card into In Progress, the MCP reads the board fresh and refuses (`WORKFLOW_START_REFUSED`, nothing written, nothing reordered) if (1) a Story above the target in the Sprint is not finished, (2) a Task above it in its Story is not finished, or (3) another Task of the same Sprint is already In Progress. The refusal carries `blocker` (`kind`: `story_order` | `task_order` | `active_task`, `ref`, `status`) and `next_step` telling what to finish, return to To Do or explicitly reorder in Taiga before retrying. Only Done and Cancelled are out of the way: a Task or Story is never skipped, so a blocked card or one in Human Decision above you halts the ones below it (RULES Guide 1/3). The FINAL Sprint Engineering Review Story is not a predecessor of the Stories listed below it, but it waits for everything above itself. Only a visible In Progress Task counts as active: GPT Validation, Request and Human Decision do not, and Request -> In Progress on the same Task is not a second active Task. Work In Progress is just what the board shows: no counter, lease, cache or stored priority exists, every decision is a fresh read, and the PO's manual moves are not subject to these agent rules.
- Sprint Engineering Review: in a governed (governance ON, strict Story vocabulary) project `taiga_milestones_create` also creates exactly one `FINAL Sprint Engineering Review` Story with exactly one integrated review Task covering architecture/ownership/DRY, SOLID/KISS/YAGNI, hardcodes/configuration, source-of-truth/state duplication, error handling/idempotency, tests/build/typecheck/lint, Sprint Issue hygiene and final readiness (blockers introduced or exposed by the Sprint become corrective work in the Sprint, pre-existing or non-blocking findings become backlog Issues, and revalidation after a fix covers only the delta and the affected gates; idempotent, reported under `engineering_review`), and every Story create/update/sprint-order/`taiga_move story_in_sprint` in a Sprint keeps it as the relative final gate (after every unfinished Story, before the Done history). A failure of this step is returned as `ENGINEERING_REVIEW_FAILED` with the persisted change, never as a clean success. `taiga_issues_promote_to_userstory` adds a `sprint_hygiene` reminder when the source Issue has no Sprint. The template, ensure/canonical-order and the fail-closed `sprintIssueFindings` helper live in `src/workflow/engineering-review.ts`. Existing Sprints are not retrofitted by side effect.
- Canonical Sprint order: unfinished Stories -> `FINAL Sprint Engineering Review` -> Done history (Done = the semantic status name from the project vocabulary, never `is_closed`). One routine, `arrangeSprint` in `src/workflow/engineering-review.ts`, owns it and only rewrites `sprint_order` rows that break the order (re-read and verified). After a governed Story `GPT Validation -> Done` (closure proven) `src/workflow/story-order.ts` sinks the Story to the very end of the history; Story create/update/reorder hooks reassert the same partition. If the reorder fails the transition still succeeds, `queue_reorder` carries `STORY_QUEUE_REORDER_FAILED` (do not retry the transition) and `STORY_DONE` is still emitted. No Sprint and non-governed projects are untouched.
- Correction path: GPT Validation -> In Progress takes a `story_correction` and moves the Story status back to In Progress (workflow open). Completed Tasks are never silently reopened; corrective work is planned explicitly. Returning to validation needs a NEW handoff; an approval citing a stale handoff (not the latest, or older than the latest correction) is refused.
- Templates: `story-start`, `story-validation-handoff`, `story-validation-approval`, `story-correction` (`workflow/templates/`, read with `taiga_workflow_template`). The Story handoff has no Task-only Blueprint field.

## PO manual moves are authoritative

The authenticated PO (role from the launcher plus the bound account, never a username in text) may move a Task or Story to any status of the project's vocabulary, including into and out of `Request`. The move carries a `po_decision` artifact, goes through the governed write boundary and is reread; the visible status then drives every later read and start rule. Old Blueprints, Handoffs and Requests are evidence only and never veto or rebuild it. GPT and Claude keep the closed `Request` state and the actor/state matrix. The PO reorders with `taiga_move`; start rules read the new visible order on the next call, with no cache or override flag.
